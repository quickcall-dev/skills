# Human taste for technical documents

## Desired character

The document must feel like a technical manual with strong visual explanation. It must not feel like a landing page, dashboard, or presentation deck.

## Layout

- Use a white or light-gray document ground.
- Keep the content width between 1120 and 1280 px.
- Keep the same left and right edges in the header, sections, tables, and diagrams.
- Use 64–88 px vertical section padding on desktop.
- Use 48–64 px vertical section padding on mobile.
- Use borders and ground changes to separate sections. Avoid heavy shadows.
- Use one dark code style. Do not use dark cards for ordinary prose.

## Navigation

- Keep the bar compact and opaque.
- Put the document identity on the left.
- Put 4–7 stage links in the center.
- Put one direct “All sections” link on the right.
- Allow the stage links to scroll horizontally on small screens.
- Do not hide the navigation inside a custom dropdown.

## Diagrams

- Place the system overview near the first architecture summary.
- Place detailed diagrams at the start of the section they explain.
- Keep the diagram title and editable-source link in a small bar above the visual.
- Allow horizontal scrolling only inside the diagram frame on narrow screens.
- Do not use a diagram as decoration.

## Content depth

Each technical stage should include:

1. Inputs.
2. Action.
3. Output.
4. Object definitions.
5. Failure behavior.
6. Test method.
7. Good and bad outputs.
8. Minimum acceptable scope.
9. Concrete test cases and oracles.

Use complete YAML or code objects. Do not use ellipses or comments that hide required fields.

## Wording

- Use sentence-case headings.
- Use a noun in each heading.
- Use one term for one concept.
- Use active voice.
- Keep instructions at 20 words or fewer when practical.
- Keep descriptive sentences at 25 words or fewer when practical.
- Do not use marketing words such as “seamless,” “robust,” or “powerful.”
